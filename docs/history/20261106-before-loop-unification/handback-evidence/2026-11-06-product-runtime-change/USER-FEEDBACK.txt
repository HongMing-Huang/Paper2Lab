我检查了你上传的 Paper2Lab 整体架构 HTML。目前的问题比较明确：

我们设计了一套相当完整的科研计算与游戏生成架构，却还没有完整设计出用户真正使用的 Paper2Lab 产品。

## 一、目前的产品设计缺少什么？

你的 HTML 包含 16 个架构模块、4 个架构视图，已经明确哪些模块负责数学事实、Agent、游戏程序和状态提交。但它没有展示实际的论文导入、数学游戏运行、学习过程或科研探索界面。页面中的“演示数据流”也只是依次切换架构模块，不是真正运行产品。

现在的架构还无法完整回答这三个问题。

## 二、我建议重新确定产品定位

# Paper2Lab — Play the Mathematics Behind Research

把数学论文变成可以探索、操作、理解和持续研究的数学世界。

产品不应直接定位为普通游戏，也不应仅定位为专业科研软件。

更合理的是：

面向数学学习者和科研探索者的 AI 数学实验室。

它包含两种自然衔接的使用方式：

- 探索模式： 不需要先理解全部公式。先通过生活化问题、数学对象与直观反馈理解论文。
- 研究模式： 可以深入数学定义、控制参数、运行实验、核对来源、分析不同论文的研究进展。

这两种方式应共享同一模型，而不是开发两款产品。

## 五、Agent 的产品角色还需要重新设计

你现在的架构把 Agent 描述为“研究者与游戏导演”，但具体用户体验仍不够。

我建议让 Qwen 在产品中拥有四种可感知的能力。

| Agent 能力          | 用户看到的实际表现               |
| ----------------- | ----------------------- |
| Researcher        | 主动发现重要公式、前置论文、值得探索的问题   |
| World Creator     | 根据数学模型生成新的世界、行为与挑战      |
| Math Tutor        | 用生活化语言解释数学现象，并逐步引导到正式定义 |
| Research Director | 根据真实实验结果提出下一次探索，并创建研究分支 |

这里不能只让 Agent 生成几个预制机制的参数。它应该能够产生新的玩法逻辑，但游戏程序仍须通过编译、受限执行和数学检查。

对于普通用户，以上角色最好由同一个可见的 AI 助手承担，而不是在界面中出现四个 Agent 聊天窗口。

更重要的是，Agent 不应该持续打断用户。它可以在首次进入世界、用户遇到困难、发现特殊现象或完成挑战时介入。

## 六、我建议第一版的完整产品体验

以你已有的 Wang–Zahl Kakeya 研究为主线，不需要换掉已经实现的大量技术。

1. 用户进入 Paper Desk。 打开论文，Qwen 用“如何让有限空间容纳不同方向的线段”引入数学问题，并指出这是有限尺度直觉实验。
2. 用户选择一个可玩入口。 系统明确展示数学对象、可以操作的自由度及挑战条件。缺少数学条件时应让用户补充，而不是伪造。
3. 进入独立 MathWorld。 用户在 3D 场景中调整管束排列，真实数学内核计算覆盖、重数和并集体积。
4. 产生游戏反馈。 玩家尝试挑战，可能成功也可能失败。系统根据真实计算结果判定，必要时展示数值误差与近似标记。
5. Agent 解释并延伸。 将实验现象映射到论文相关概念，提供“继续挑战”“查看推导”“研究前置工作”等自然选择。
6. 保存到研究空间。 实验、参数、结果、论文来源和 Agent 解释形成可恢复的研究记录，允许下一次继续探索。

这里需要明确一个产品定位上的取舍：Kakeya 是核心展示案例；正定二次型可以作为第二个可生成数学世界的技术验收案例。

这样既维持封面、论文、作品故事的一致性，也能证明底层并非完全针对 Kakeya 写死。

## 七、当前架构应该怎么改？

我不建议现在继续扩充你 HTML 中的 16 个系统模块。

这些模块在工程职责上基本可以保留，但应该在它们之上新增一层真正的 Product Experience Architecture。

| 产品层                 | 必须确定的内容                 | 当前优先级  |
| ------------------- | ----------------------- | ------ |
| Paper Desk          | 导入、研究问题、可玩入口、来源与信任状态    | P0     |
| MathWorld           | 游戏世界、玩家输入、玩法目标、反馈、失败与成功 | P0     |
| Learning Experience | 生活直觉、公式解释、逐步提示、数学意义     | P0     |
| Agent Experience    | 主动生成、引导、修复、下一轮研究        | P0     |
| Research Space      | 实验保存、对比、研究脉络和继续探索       | P1     |
| System Atlas        | 架构、任务、数据所有权、运行证据        | 内部开发工具 |

你上传的 SYSTEM ATLAS 应该保留，但它应当服务于开发团队，不应该代替真正的产品原型。

另外，我建议比赛阶段特别注意 Intel 本地 AI：它应当出现在真实的论文检索或解释交互中，并有可核验的本地推理记录，而不是只在架构图中画出端云协同。

## 最终建议

现在最需要做的不是继续开发 Agent Harness，也不是立刻换 PlayCanvas 或 Godot，而是确定 Paper2Lab 的完整产品体验。

我建议下一次设计交付只围绕四个真正的产品画面完成：

论文入口、数学实验世界、AI 引导与数学理解、研究记录与继续探索。

每个画面必须说明用户看到什么、能做什么、操作后真实发生什么、失败时怎样处理、Agent 何时介入，以及科学内核怎样提供依据。

只有完成这一层设计，再将现有 Math IR、World Program、Scientific Runtime 和 Agent 接进去，Paper2Lab 才会从一张复杂的架构图，变成一个真正能被用户理解、进入、玩起来并持续使用的产品。
